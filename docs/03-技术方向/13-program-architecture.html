程序架构

一台 FRC 机器人的程序通常有几十个文件、上万行代码，由好几届学生接力维护。好的架构让代码易读、易改、易调试。这一篇介绍 WPILib 的机器人生命周期和最主流的 Command-based 框架，以及日志、Git 协作和代码规范。

资料整理于 2026 年 10 月代码示例以 Java 为主

01为什么需要架构

  • 机器人同时在做很多事：底盘在跑、取件在转、发射器在加速，程序要同时管好它们，又不能互相打架
  • 同一个动作有多种触发方式：驾驶员按键、自动程序、传感器条件都可能触发"取件"，逻辑最好只写一次
  • 代码要能交接：学生每年都有毕业的，清楚的结构让新同学能快速接手
  • 比赛现场要能快速改：结构清楚，才能在十几分钟内定位问题、改一个参数而不引入新错误

02程序的生命周期

WPILib 的机器人程序以固定周期运行，默认每 20 毫秒执行一轮（50 Hz）。根据机器人当前的模式，框架会调用不同的方法：

方法什么时候调用常放什么
robotInit()程序启动时一次创建所有对象、下发配置（现在多放在构造函数里）
robotPeriodic()任何模式下每 20 ms运行命令调度器、更新日志和仪表盘
disabledInit / Periodic机器人禁用时停止所有输出、准备自动程序
autonomousInit / Periodic自动阶段启动选好的自动程序
teleopInit / Periodic手动阶段取消自动程序，交给驾驶员
testInit / Periodic测试模式单独测试某个机构、做系统辨识

每一轮都必须在 20 ms 内跑完。如果某段代码太慢（比如在循环里等待、做大量计算），整个机器人都会变得迟钝，Driver Station 会提示循环超时（loop overrun）。所以程序里绝不能用等待或死循环，所有动作都要拆成"每 20 ms 做一小步"。

03Command-based 框架

Command-based 是 WPILib 推荐、FRC 最主流的程序结构。它把程序分成三种角色：

角色是什么例子
Subsystem 子系统一个机构的代码封装：拥有它的电机和传感器，提供"设置速度""读位置"这类基础方法Drivetrain、Intake、Shooter、Arm
Command 命令一个有开始、过程和结束的动作。声明自己需要哪些子系统"取件直到有道具"、"手臂转到 45°"
Trigger 触发器决定命令什么时候开始、什么时候停止按住 A 键时取件；道具进入时自动收回
CommandScheduler 调度器每 20 ms 运行所有活动的命令，处理冲突新命令需要已被占用的子系统时，打断旧命令

命令的组合

简单的命令可以像积木一样组合成复杂动作，这是 Command-based 最强大的地方：

  • andThen / Commands.sequence：依次执行
  • alongWith / Commands.parallel：同时执行，全部结束才算结束
  • raceWith：同时执行，任何一个结束就全部结束
  • deadlineFor：同时执行，以某一个为准
  • until、withTimeout：加上结束条件或超时

04项目结构

用 WPILib 的 Command Robot 模板创建的项目，结构大致如下：

src/main/java/frc/robot/ ├── Main.java 程序入口，一般不用改 ├── Robot.java 生命周期方法，运行调度器 ├── RobotContainer.java 创建子系统，绑定按键，提供自动程序 ├── Constants.java CAN ID、尺寸、PID 参数等常量 ├── subsystems/ │ ├── Drivetrain.java │ ├── Intake.java │ └── Shooter.java └── commands/ 较复杂的命令（简单的可以写在子系统里） └── ScoreSequence.java
  • RobotContainer 是"总装配"：所有子系统在这里创建，手柄按键在这里绑定到命令。想知道"按哪个键做什么"，看这一个文件就够
  • Constants 集中放参数：比赛现场改参数只动这一个文件
  • 每个机构一个子系统：和机械上的机构一一对应，分工清楚

05一个完整的例子：取件

子系统封装硬件，并提供返回命令的方法（命令工厂）：

public class Intake extends SubsystemBase {
    private final TalonFX roller = new TalonFX(Constants.INTAKE_ROLLER_ID);
    private final DigitalInput beamBreak = new DigitalInput(Constants.INTAKE_SENSOR_PORT);

    public boolean hasPiece() {
        return !beamBreak.get();          // 光被挡住 = 有道具
    }

    // 转滚轮，直到检测到道具，结束时停转
    public Command intakeUntilPiece() {
        return run(() -> roller.setVoltage(8.0))
                .until(this::hasPiece)
                .finallyDo(() -> roller.stopMotor());
    }
}

在 RobotContainer 里把按键绑定到命令：

CommandXboxController driver = new CommandXboxController(0);
Intake intake = new Intake();

// 按住 A 键取件，松开或拿到道具时停止
driver.a().whileTrue(intake.intakeUntilPiece());

// 拿到道具时让手柄震动一下，提醒驾驶员
new Trigger(intake::hasPiece).onTrue(rumbleDriver());

同一个 intakeUntilPiece() 也可以直接放进自动程序里使用。具体类名和接口以当年的 WPILib 和厂商库为准；比如传感器接到 SystemCore 的 SmartIO 后，读取方式可能和这里不同。

06多机构协调

当电梯、手臂、取件互相影响时（比如手臂只有在电梯升起后才能翻转，否则会撞到底盘），常见的做法有：

  • 把相关机构合成一个"上层结构"（superstructure）：由它统一规划动作顺序，外部只说"去放置高位"，内部决定先升电梯还是先转手臂
  • 用状态机描述目标状态：比如"收起 / 取件 / 准备低位 / 准备高位"，每个状态对应一组机构位置，状态之间的切换路径预先规划好
  • 在子系统里加安全检查：即使上层逻辑出错，子系统自己也拒绝进入危险位置

07日志与遥测

机器人在场上出问题时，往往没法当场复现。好的日志能在赛后还原当时发生了什么：

  • WPILib 数据日志：自动记录 Driver Station 数据和 NetworkTables 数据，保存到主控制器上，赛后用 AdvantageScope 打开分析
  • AdvantageKit：社区广泛使用的日志框架，能记录所有输入，赛后"回放"整场比赛，甚至修改代码后重新运行看结果
  • 2027 年的变化：WPILib 2027 用新的 Telemetry 和 Tunables 接口取代了 SmartDashboard，用来发布数据和在线调参
  • 该记什么：每个机构的目标值和实际值、电流、传感器读数、当前命令、机器人位姿。调 PID、查断线都离不开这些曲线

08Git 与协作

  • 所有代码放在 Git 仓库里：通常托管在 GitHub 上，队伍建一个组织账号，学生用各自的账号协作
  • 小步提交：每完成一个小功能就提交一次，写清楚改了什么
  • 用分支开发新功能：主分支始终保持"能上车"的状态，新功能在分支上开发，测试通过后再合并
  • 代码评审：用 Pull Request 合并代码，至少有一位同学或 mentor 看过。这是家长 mentor 很好的参与方式
  • 给比赛版本打标签：每场比赛用的版本打一个标签，出问题时能马上退回
  • 比赛现场也要提交：现场临时改的参数，赛后一定要提交，不要只留在笔记本电脑上

09代码规范

  • 单位要明确：变量名带上单位（heightMeters、angleRadians），或者使用 WPILib 的单位库，避免米和英寸、度和弧度混用
  • 不写"魔法数字"：所有参数放进 Constants 并起好名字
  • 子系统不直接互相调用：机构之间的协调交给命令或上层结构，子系统保持独立
  • 统一格式：用自动格式化工具（比如 Spotless）保持代码风格一致
  • 写给下一届看：关键逻辑写清楚注释，说明"为什么这样做"

10常见问题

按了按键，命令开始了一下就停了
可能是另一个需要同一子系统的命令（比如默认命令）把它打断了，或者命令的结束条件一开始就满足。用日志查看当前运行的命令。
Driver Station 一直提示 loop overrun
某段代码太慢。常见原因：在周期方法里等待、频繁读写文件、打印大量信息、每轮都创建新对象。
两个机构同时动时撞在一起
缺少协调逻辑。把相关机构合并到上层结构里统一规划，并在子系统里加安全限制。
比赛现场改了参数，下一场又变回去了
改的是另一台电脑上的代码，或者没有重新部署、没有提交。比赛时固定一台部署用的电脑，改完立刻提交。
